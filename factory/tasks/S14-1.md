## Goal
The app's driver tests stop disturbing the person at the keyboard. A driver build reads
`WATANE_DRIVER_SCREEN` (`hidden` | `background` | `front`) once at startup. In `hidden` its
windows are built invisible, in `background` they show but never take focus, and in both it runs
as an Accessory app (no Dock icon, never activates). `front` behaves as today. Tests declare
their mode through the constructor they call, never through an `if` in a test body. Tests that
need real focus or stacking use `App::front`, are `#[ignore = "front: takes the screen"]`, and
wait for the human to step away before they start. A release build is unchanged and has no driver.

## Acceptance
- AC1 Default run is quiet: `cargo test -p watane-app --features driver` (no `--include-ignored`)
  passes, and every GUI test it runs starts the app through `App::start` (hidden) or
  `App::background`. Prove "hidden" in one test: after `App::start`, driver `windows` shows
  `main` with `visible: false` and `focused: false`. Prove "no Dock icon" by a check that the
  app's activation policy is Accessory in that mode (expose it on the driver `windows` or a new
  `screen` op, e.g. `{"mode":"hidden","accessory":true}`; your choice, document it in TECHNICAL 10).
- AC2 Background: one test with `App::background` shows `main` `visible: true`,
  `focused: false`, and the mode's accessory flag true.
- AC3 Front tests: every assertion on `focused == true`, `visible == true`, `document.hasFocus()`,
  stacking above another window, or the 800 ms approve delay lives in a test that starts with
  `App::front` and carries `#[ignore = "front: takes the screen"]`. At least: `gui_isolation`
  ac1 (consent above hostile, takes focus), `gui_shell` ac4 (approve delay, deny focus), the
  consent-takes-focus check now in `gui_shell::consent()`, and `gui_shell` ac2's "opening an open
  mod focuses it" loop (split it into its own front test; the rest of ac2 stays hidden). Every
  other assertion of today's tests is kept, in a hidden or background test. No behaviour loses
  its test.
- AC4 `App::front` waits until the human has been idle at least 30 s (`ioreg -c IOHIDSystem`,
  `HIDIdleTime` in ns), printing `waiting for you to step away` once to stderr, and panics with
  a clear message after 10 minutes. It never skips. Put the idle parsing in a small pure
  function with a unit test (in `tests/support_selftest.rs`) on a sample `ioreg` line.
- AC5 Helpers: in `src/views.rs` one function applies the mode to a `WebviewWindowBuilder`
  (used by main, mod and consent builders), and one function replaces the direct `set_focus`
  (in `open_mod`) and `set_focus` + `request_user_attention` (in `sync_consent`) calls and acts
  only in `front`. Without feature `driver` both behave as today's code (builder unchanged,
  focus calls made). The mode is read once (driver setup or `AppState`), not per window.
  Setup sets `ActivationPolicy::Accessory` for every mode except `front`.
- AC6 Release: `cargo build -p watane-app --release` succeeds and the env var name
  `WATANE_DRIVER_SCREEN` does not occur in the release binary (`strings ... | grep` empty).
  This is a build check for the validator; no test needed.
- AC7 Check first, and record in `app/NOTES.md`: whether a hidden WKWebView window still
  finishes page loads, runs driver `eval` JS and fires timers on time (the hostile page's poll
  loop, the consent page's 800 ms delay). Any test that fails hidden for this reason uses
  `App::background` instead; name each such test in NOTES.md.
- AC8 clippy `--all-targets --features driver -D warnings`, `cargo fmt --check` pass.
  `--include-ignored` front tests pass when run (the foreman runs them once; you need not).

say so under QUESTIONS; the validator runs them.

## Interface
Provides (fixed), in `tests/support/driver.rs`:
`App::start(home: &Path, env: &[(&str, &str)]) -> App` (hidden; unchanged signature),
`App::background(home, env) -> App`, `App::front(home, env) -> App` (same signature). Each sets
`WATANE_DRIVER_SCREEN` itself, overriding the caller's environment. Env values: exactly
`hidden`, `background`, `front`; unset or unknown in a driver build means `hidden`.
