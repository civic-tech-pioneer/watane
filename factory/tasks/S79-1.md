Subsystem: dist
Effort: medium
Depends on: none
Slice: S79 — Bob installs from a site published minutes ago, and a new base sticks

## Goal
A GitHub Pages site published minutes ago answers 503 for a while. After this task dist tries a
read that got an HTTP 5xx twice more with a short backoff, all inside the read's own timeout
(4.5), so Bob's install goes through once the host is ready, and a host that keeps failing still
fails within the same deadline, naming the URL. And when Bob opens, follows or chooses a link that
names a new base for a channel dist already knows (say Alice moved from raw.githubusercontent.com
to her Pages site), the new base is added to that record's `bases` instead of being dropped or
replacing the old one, and every later read of the channel checks every base (deputy decision S54
in factory/PLAN.md: learned bases are appended; every base is checked).

## Acceptance
AC1 A `tiny_http` server on 127.0.0.1:0 that answers 503 to the first GET of a file and 200 with
    the real bytes afterwards: `follow` (and `open_link` for a release) of a link to it succeeds,
    and the release installs (fetches) with verified bytes.
AC2 A server that always answers 503 for `head`: `follow` fails with `DistError::Http { url, status:
    503 }` whose `url` is the head URL; the server saw exactly 3 GETs of it; the call returned
    within `entry_timeout` plus a small slack (set `entry_timeout` to e.g. 3 s in the test).
AC3 Deadline: with `entry_timeout` shorter than the backoff sum (e.g. 300 ms) and a server that
    always answers 503, the call returns an error within about `entry_timeout` (plus slack), having
    made fewer than 3 GETs; no retry starts after the deadline.
AC4 Only 5xx retries: a 404 gives `NotFound` after 1 GET; a 403 gives `Http` after 1 GET; a
    timeout or network error is not retried (one attempt).
AC5 Bob follows Alice through base A; Alice's channel is then also served at base B (a second
    server with the same files, B newer by one entry). `follow` (or `open_link`) with a link of
    the same key and base B: the record's `bases` is `[A, B]` with the highest-head base first
    after the read (so `[B, A]` here), `base` equals `bases[0]`, and the new entry is ingested.
    Before this task the old base was replaced (`follow`) or the link's base ignored
    (`open_link` of a known channel).
AC6 After AC5, `refresh` reads both bases: if A goes down (server dropped) the channel is still
    `Current` from B; if B goes down it is read from A (the outcome is the best one, 5.9).
AC7 A link whose base is already in the record (or equals `base`) changes nothing in
    `follows.json`. A record keeps at most 4 bases: a fifth link's base is appended and the
    oldest learned base after the front one is removed.
AC8 `choose_index` with a new base for a known chosen or followed channel learns it the same
    way. Listings still never change a followed or chosen record's bases (5.9, existing tests).
AC9 A step 3 / step 4 `follows.json` (followed record without `bases`) reads unchanged and is
    read from `base` only, as today.

## Interface
No public signature changes. `DistError::Http { url: String, status: u16 }` keeps its fields and
its text (app and node match it). `Options` gains no field: the backoff is two fixed waits in
http.rs (e.g. 250 ms, then 500 ms), each cut short by the read's deadline; the deadline is the
first attempt's start plus the read's timeout, and each attempt's `timeout_global` is the time
left. A blocking `std::thread::sleep` inside `get` is allowed (rule 7 bans background timers and
threads, not a wait in the caller's thread); say so in section 12.
`follows.json` stays version 1; `bases` keeps its serde default `[]`.

## Out of scope

- `read_link` (preview) learning a base; dev's publish suggesting a Pages base (PLAN S54 note).
- Changing the 4-base cap for listed records or the local-address rules.
