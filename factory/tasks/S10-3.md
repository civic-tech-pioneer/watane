## Goal
Alice can start `watane-app --home <dir>` on a new home and see the main window: an empty
launcher (or, from a fake catalog, one entry per mod that opens the mod's page in a window of
its own) and her two mark words in the header. Every request put into the `Broker` shows in the
consent window, one at a time, above all other windows, with Deny focused and Approve dead for
800 ms after each focus; closing it answers Deny. A test drives all of this through the driver
(feature `driver`), which a release build refuses.

## Acceptance
Window tests (`tests/gui_shell.rs`, `#![cfg(feature = "driver")]`) spawn
`env!("CARGO_BIN_EXE_watane-app")` with a temp home and `--port 0` and use `tests/support/`.
- AC1 (S1) A new home: after `{"event":"ready",...}`, `eval` in `main` finds no mod entry in the
  launcher; the header text is two words of `WORDS` separated by one space, equal to the file
  `<home>/app/mark` without its newline; `<home>/mods/` does not exist or is empty.
- AC2 With `WATANE_APP_FAKE` naming two mods (one with a `page`, one without), the launcher
  shows both names; clicking the open control of the one with a page opens a window
  `mod-<local>` at that page URL with title `<name> — local` (or `— <party name or
  fingerprint>`); opening it again gives no second window and the existing one is focused
  (APP-F-7). The mod without a page has no open control, and `mod_open` for it is `not_found`.
- AC3 (S3) A driver `ask` with an `Install` request opens the window `consent`; driver `close`
  of `consent` makes the `ask` return `{"answer":"deny"}`; `consent` no longer exists.
- AC4 (S4) The consent window got focus at time t (the test's own clock, taken when `wait`
  returns after the focus): a click on Approve at t + 100 ms sends no answer (the `ask` is still
  open, the Approve control is `disabled`); a click at t + 900 ms returns `{"answer":"approve",
  "withheld":[]}`. Deny has the focus at load; the page has no `<form>`.
- AC5 An `Install` request of two mods (one local, one with `publisher`, `release` and
  `replaces`, grants of all four kinds, one `new`, a `uses` line) and a `Sign` request of each
  `Statement` show every field of TECHNICAL 6.3 and 6.2 (DOM text via `eval`), and the mark.
  Unchecking one grant and approving returns that grant as `withheld: [{local, key}]`.
- AC6 Two `ask`s at once: the consent window shows the first; after its answer, the second
  (APP-F-17). Driver `quit` with a request open answers it `deny` and the app exits 0.
- AC7 A mod named `<img src=x onerror=alert(1)>` in the fake catalog and in a request shows as
  that literal text in `main` and `consent`; no `img` element exists.
- AC8 `tests/static_config.rs` (no feature needed) checks every item of its row in TECHNICAL 11
  and section 14, with the stage A command lists (Interface below) as literals.
- AC9 `cargo build --release --features driver` fails with the `compile_error!` message (a test
  in `static_config.rs` may check the source line; the build itself is checked by hand and by
  the validator). `cargo test -p watane-app`, `cargo test -p watane-app --features driver`,
  clippy `--all-targets --features driver -D warnings`, `cargo fmt --check` pass.

## Interface
Takes (fixed, S10-1): `watane_app::consent::*`, `watane_app::mark::*` as TECHNICAL 6.
Provides (fixed, used by S10-4):
- Commands in `build.rs` and `capabilities/main.json`: `status`, `mods_list`, `mod_open`,
  `mod_disable`; `capabilities/consent.json`: `consent_get`, `consent_answer`. `mod_disable`
  joins stage A (decided for S10): Core calls `views::close_mod` first, then marks the fake
  mod `enabled: false`. Update the table of TECHNICAL 7 (`mod_disable`: stage A).
- `src/core.rs`: `pub(crate) struct Core` with `mods() -> Vec<ModView>`, `get(local) ->
  Option<ModView>`, `disable(local) -> Result<(), CmdError>`; stage A backs it with
  `src/fake.rs` (env `WATANE_APP_FAKE`: JSON `{"mods": [ModView]}`, camelCase as section 7;
  missing env = no mods). Only `core.rs` knows `fake.rs`.
- In the main page each launcher entry is an element with `data-local="<local>"`; its open
  control is a `button.open`, its disable control a `button.disable`.
- `tests/support/mod.rs` with `pub mod driver;` and `tests/support/driver.rs`:
```rust
pub struct App { pub home: PathBuf, pub port: u16, /* child, reader */ }  // kills the child on drop
impl App {
    pub fn start(home: &Path, env: &[(&str, &str)]) -> App;  // waits for ready; panics on failed
    pub fn eval(&self, label: &str, js: &str) -> serde_json::Value;
    pub fn wait(&self, label: &str, timeout: Duration) -> bool;
    pub fn windows(&self) -> Vec<serde_json::Value>;
    pub fn close(&self, label: &str);
    pub fn log(&self) -> serde_json::Value;
    pub fn ask(&self, request: serde_json::Value) -> AskHandle; // .wait(timeout) -> Option<Value>; .is_open()
    pub fn quit(self) -> std::process::ExitStatus;
}
```
  A test file uses it with `mod support;`. Never a fixed sleep to wait for the app; a `wait`
  loop with a timeout of 30 s or more is fine (factory/README "Timing tests": the S4 clock
  test is not such a limit test; keep it in the normal run).
