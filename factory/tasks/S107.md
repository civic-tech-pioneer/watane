Slice: S107 — a base reached through dist's own links is never given

## Goal

Only a participant-supplied link can give a channel base. Derived follows and listing preflight apply the listed-read policy to bases that lack explicit permission.

## Acceptance

1. Following a derived link does not give its base, regardless of prior records or pruning.
2. Following, opening, or choosing an index from a participant-supplied link can explicitly give its base.
3. List and include preflight use the listed read budget and address policy before asking for confirmation.
4. Legacy records reopen conservatively and no longer write the seen history, tombstones, or filter.

## Spec

dist/TECHNICAL.md 4.4, 5.4, 5.9, 5.11 and spec/TECHNICAL.md 6.

## Interface

`Dist::follow_derived(&self, link: &Link) -> Result<RefreshReport, DistError>`.

## Files

dist source, contract and tests.

## Changed tests

- The S105 r3, r4 and prune tests in `dist/src/http.rs` become defensive checks of stored authorization and listed reads after legacy load, mirror eviction and pruning. Explicit follows and index choices can authorize an already listed base.
- `ac1_follow_choose_and_a_learned_link_mark_the_base_given` checks that opening an already held base can give it. `ac6_explicit_links_use_regular_entry_cap` checks both new and previously listed participant links.
- `ac4_provider_trust_order`, `ac5_listed_record_dead_base_falls_to_provider_bases` and `ac6_read_link_no_follow` expect no provenance write. The holder rollback test checks that a legacy tombstone is discarded.
- The listing request tests opt their fixtures into listed reads on loopback. Tests exclusively for the removed heuristic are retired. Durability tests still cover record writes and pending work.

## Out of scope

Windows build configuration and the network address classifier.
