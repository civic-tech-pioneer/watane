## Goal
The identity key's two crash and fsync gaps from S109's review close. Re-checked against main at
b09c909 by the foreman: S109 P2.1 (rustix's Libraries line, `log/TECHNICAL.md` 9 has
`default-features = false`), P2.2 (`log/src/identity.rs`'s `//!` cites 4.7) and P2.3 (no
`publish_key` wrapper is left; `write_key` in `log/src/identity/unix.rs` calls `renameat`
directly) are already on main: no work. What remains:
1. A crash between creating `.identity.key.<32 hex>.tmp` and its rename leaves that file (it holds
   a key seed) in the log directory forever. Decision (foreman, inside log): the next `open`,
   `open_keyless` and `restore_identity`, under the directory lock and through the anchor, remove
   each leftover entry whose name is exactly `.identity.key.<32 lowercase hex>.tmp` (sweep). A
   sweep that cannot remove one entry (a directory of that name, a permission error) does not fail
   the call; nothing else in the directory is touched.
2. `Log::restore_identity` sets `inner.key` only when `identity::replace` returns Ok. When the
   rename published the new key but the directory `fsync` after it failed, the file holds the new
   key while memory still signs with the old one. Decision: memory follows the file. After the
   rename, the new key is the one in memory, whether the following sync succeeds or not, and the
   sync error is still returned. A failure before the rename leaves the old key on disk and in
   memory. Same on Windows (its publish step is the rename).

## Acceptance
AC1 A log directory holding a stray `.identity.key.<32 hex>.tmp` (regular file, 0600) from an
    earlier run: `Log::open` succeeds, the identity is the one in `identity.key`, and the stray
    file is gone afterwards. Same for `open_keyless` on a keyless directory.
AC2 A file named `.identity.key.notes.tmp`, `identity.key.bak` or `.identity.key.<31 hex>.tmp` is
    left in place by the same open (only the exact pattern is swept).
AC3 A directory named `.identity.key.<32 hex>.tmp` does not make `open` fail; it is left.
AC4 `restore_identity` whose directory sync after the rename fails (a `#[cfg(test)]` failure hook
    at that step, Unix unit test is fine): the call returns an error, `identity()` then returns the
    restored key's public key, and a reopen of the directory reads the same key.
AC5 `restore_identity` failing before the rename (for example at the temporary file's write or
    `sync_all`, via the same kind of hook): the error is returned, `identity()` is still the old
    key, `identity.key` still holds the old seed, and no `.tmp` is left.
AC6 `log/TECHNICAL.md` 4.7 states the sweep (when, which names, that its failure does not fail the
    call) and that after the rename memory holds the published key even if the sync fails.
