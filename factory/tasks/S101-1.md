Slice: S101 — A preview starts in a container without IPv6.

## Goal
Bob's cloud agent runs `watane --preview` (or `watane-dev serve`, which runs the same host
server) in a Linux container whose kernel has no IPv6 loopback. Today the host refuses with
`port_in_use`, because binding `[::1]:<port>` fails. After this task the server serves
`127.0.0.1:<port>` alone when, and only when, binding `[::1]:<port>` fails with
`std::io::ErrorKind::AddrNotAvailable` (the machine has no `::1`) or with the OS error
EAFNOSUPPORT (the kernel has no IPv6 at all; Rust reports it as kind `Uncategorized`, raw OS error
97 on Linux, 47 on macOS, 10047 `WSAEAFNOSUPPORT` on Windows). Both mean nobody can bind `::1`.
This cloud container gives EAFNOSUPPORT. It then prints one line on stderr saying so. Every other `[::1]` failure (address in use, permission
denied, anything else) stays `port_in_use` exactly as today, and the 8-try clash loop for port 0
is unchanged for those failures.

## Acceptance
AC1. A unit test of the decision (a small private function in `host/src/server.rs`, for example
     `fn v6_absent(error: &std::io::Error) -> bool`): `AddrNotAvailable` -> serve v4 only;
     `Error::from_raw_os_error(EAFNOSUPPORT)` (the platform's value; `libc::EAFNOSUPPORT` only if
     `libc` is already a host dependency, else `cfg` constants) -> serve v4 only; `AddrInUse` -> `port_in_use` (with port 0: try again); `PermissionDenied` and any
     other kind -> `port_in_use`. Each kind compared with a literal expectation.
AC2. On a machine without `::1` (this cloud container), `watane --preview <dir> --port 0` prints
     its ready line, and `GET http://127.0.0.1:<port>/api/status` answers 200; with a fixed
     `--port`, the same. The program prints on stderr one line, exactly
     `watane: no IPv6 loopback (::1); serving 127.0.0.1 only`. The ready line's JSON is unchanged
     (no new field).
AC3. On a machine with `::1` nothing changes: both addresses are bound, port 0 gives the same port
     on both, and `[::1]` answers (the existing tests, run in CI).
AC4. When `[::1]:<port>` is held by another socket (AddrInUse) with a fixed port, `serve` still
     returns `port_in_use` and binds nothing. Cover this in a test that runs only where `::1`
     exists (bind `[::1]:0` first; if that fails with AddrNotAvailable, return early with a
     comment), so CI proves the in-use branch.
AC5. The host and dev test suites that failed in the cloud for lack of `::1` now pass here, except
     tests that themselves connect to `[::1]` (they keep checking `[::1]` wherever `::1` exists;
     see Changed tests).
