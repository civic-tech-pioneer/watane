## Goal
dist's network tests stop timing out when the machine is busy (S28, S29 `restore.rs` ac11, S35).
`support::fast_options()` today sets `entry_timeout` 300 ms and `package_timeout` 1 s for every
test; under a parallel `cargo test` a plain loopback GET can take longer. After this task the
shared test options use timeouts that hold under load, and only a test whose point is a timeout
sets a short one, next to the stall that trips it. No product code changes.

## Acceptance
- AC1 `support::fast_options()` (keep the name, or rename it everywhere in `dist/tests`) sets
  `entry_timeout` and `package_timeout` of at least 10 s; it keeps `max_package: 4096`.
- AC2 `fetch.rs` `ac9_fetch_limits_and_timeout` still gets `DistError::Timeout` with the package
  url: it sets its own short `package_timeout` (e.g. 300 ms) on the home it fetches with, and the
  stall stays well above it (`Mode::Stall` 3 s or more). Any other test that expects
  `DistError::Timeout` does the same (search `Timeout` and `Mode::Stall`; today ac9 is the only
  one).
- AC3 The per-test overrides `entry_timeout: from_secs(3)` (`index.rs` 273, 475; `support`
  `Home::offline` 190) go away, since the default now covers them; nothing else in those tests
  changes.
- AC4 `cd dist && for i in 1 2 3 4 5; do cargo test -- --include-ignored || break; done` passes
  all 5 runs, with test threads at the default (parallel). Run it while another heavy job loads
  the machine if one is running; report the wall time of one run before and after (the suite
  must not get noticeably slower: no test may now wait on a 10 s timeout that used to fire at
  300 ms; if one does, give that test its own short timeout as in AC2).
