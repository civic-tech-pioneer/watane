## Goal
Two pkg refusals still mislead. (1) When the part directory `ui` (or `wit`) of a mod folder is
itself a symbolic link, `Mod::read` reports two problems: the link (rule `path`, file `ui`) and
then the 4.6 parts rule (`ui/ must be a directory containing a regular ui/index.html`). After
this task it reports only the link: a part that is a refused link gets no second, derived
violation for the same part. (2) When release bytes run out inside a value whose start the
reader already saw (a text string whose header announces 5 bytes but only 1 follows; a 32-byte
key cut off; an integer header with its bytes missing), the error says the value was cut short,
not just "found end of input" as if nothing was there.

Decided here (not by you):
- A part (`mod.toml`, `deps.json`, `logic.wasm`, `ui`, `wit`) that is a symbolic link gets
  exactly one violation: rule `path`, file = the part's name, the existing link message. No
  `parts` violation is added for that part. Other parts keep their own violations.
- Release reader: when the decoder had seen the type of the next value (`datatype()` was `Ok(t)`)
  and the read then fails with end of input, `found` is `<describe(t)> cut short by the end of
  input` (e.g. `bad release body: slug: expected text, found a text string cut short by the end
  of input`). When nothing was there at all, it stays `end of input`. `malformed()` stays a plain
  wrapper (S46 already moved the context to the call sites; keep it so).

## Acceptance
Tests in a new `pkg/tests/s49.rs` (use `support::built_fixture("hello")` as `s46.rs` does).
- AC1 On the `hello` fixture copy with `ui` moved to `ui2` and `ui` a symlink to `ui2` →
  `Mod::read` gives `ModError::Invalid` with exactly one violation: rule `Path`, file `ui`, the
  link message. Same with `ui` a link to a path outside the folder, and with a dangling link.
- AC2 Same for `wit` (moved, linked): exactly one violation, rule `Path`, file `wit`. If today's
  code gives more than one (WIT rule, parts rule), those go.
- AC3 `Release::decode` of the golden release truncated inside the slug text (`8c 01 65 68`) →
  `bad release body: slug: expected text, found a text string cut short by the end of input`
  (take the exact `what` from the code). Truncated inside the package id → `package id: ...,
  found a byte string cut short by the end of input`. `[0x8c, 0x19]` → `format: ..., found an
  unsigned integer cut short by the end of input`.
- AC4 `[]` and `[0x8c]` keep their S46 messages exactly (`found end of input`).
- AC5 Every existing pkg test passes unchanged (`cargo test -p watane-pkg -- --include-ignored`).
