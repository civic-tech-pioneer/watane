## Goal
Three small things an agent tripped on in S11 work as it expects: a dependency cycle or a
self-dependency says how to get out of it; `check` shows the path of a local provider; and
`add <provider> --dir <mod>` reads `<provider>` from the folder where the agent ran the command,
like any shell path.

## Acceptance
- AC1 `mod.self_dependency` has a fix: `Pass the folder of another mod to add`.
- AC2 `mod.dependency_cycle` has a fix that names the edge to cut. From `add` (nothing changed):
  `Do not add <provider slug>: it already depends on this mod`. From traversal (`test`/`serve`/
  later `install`, a cycle already on disk): `Remove mods:<slug> from deps.json and wit/deps/<slug>/
  in <absolute folder>` for the last edge of the cycle (the one that closes it). Literal unit
  tests in `deps.rs`; TECHNICAL 2.2's row gets the fix texts.
- AC3 `check --json` on a mod with a local provider recorded in `.watane-dev.json` reports
  `providers[].path` as recorded (for example `"../reading-list"`), as TECHNICAL 2.4 **check**
  shows; null only when `.watane-dev.json` names none for that slug. Test at the lowest level
  that shows it.
- AC4 `add <provider>` resolves a relative `<provider>` against the current folder, not `--dir`.
  `.watane-dev.json` still stores the path relative to the mod folder (9.5 step 3). Test: from a
  parent folder holding `a` and `b`, `add a --dir b --json` succeeds and stores `../a`. Any
  existing test that asserts resolution from `--dir` changes with it; name it in your report.
  TECHNICAL 9.5 says so in one sentence.
- AC5 One line under "Spec gaps resolved" in `dev/AGENTS.md`. Default `cargo test -p watane-dev`,
  clippy `--all-targets --all-features -D warnings`, `cargo fmt --check` pass.
