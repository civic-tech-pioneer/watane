## Goal
Two gaps S72-2 found while building `watane-node`: (1) a machine that joins with a pairing code
does not keep the anchor's address, so `watane-node join` followed by `watane-node run` finds the
anchor only through mDNS, a relay or the DHT, and on a plain LAN with mDNS off (or on loopback) it
finds nobody. `Core::learn_addr` (net/src/sync.rs) ignores a machine that is not in the device
list, and during `join` the joiner has no list yet. After this task, a successful `join` stores the
address at which the anchor was reached (as `learn_addr` would once listed), so a reopened home
reaches the anchor at its stored address. (2) `Net` has no way to read its switches, so the program
reads `<home>/net/book.json` itself. After this task, `Net::options()` gives the current `Options`
(`on`, `relays`, `dht`, `relay_server`, `limits`) as `set_options` last stored them, and `book.json`
stays net's own file.

## Acceptance
- AC1 (integration, net/tests/pair.rs or reach.rs, `MemHoldings`) a machine joins the anchor with a
  pair code; it is closed and reopened (same home, `on`, mDNS off, no relay, no DHT, no
  `add_addrs`): it connects to the anchor (`hello` succeeds, or `PeerUp`) within a few seconds.
  It fails on today's code.
- AC2 the stored address obeys 4.5 as for any listed machine (at most four, newest first); only the
  anchor's address is stored by a join, nothing for machines it has not reached.
- AC3 (unit or integration) `Net::options()` after open returns what open was given merged with
  `book.json` as 5.1 / node Q1 say, and after `set_options(o)` returns `o`'s switches; with
  `Options.on` false at open it says `on: false`.
- AC4 net/TECHNICAL.md 3 lists `pub fn options(&self) -> Options`; 5.5 (pairing) says the joiner
  stores the anchor's address.
- AC5 `cargo test -p watane-net` passes, wall time near ~40 s (report it); clippy and fmt clean.
