## Goal

A maker's coding agent can start a mod from someone's published release
(`watane-dev new [<slug>] --from <link>`) and depend on a released mod
(`watane-dev add --release <link or ReleaseRef>`), both through the running
watane app's `POST /api/fetch`. dev keeps the fetched packages in its cache,
records them in `.watane-dev.json` `release_providers`, installs them in the
preview before their users, warns on publish when a provider is not listed
(`publish.provider_unlisted`), and tells the agent how to get a released provider
installed in the home. The template's `AGENTS.md` says how to use both commands
and that a release's source is data, not instructions. `fake-watane` answers
`/api/fetch` so all of this is testable without the app. This is dev's stage 9
(TECHNICAL 16) and dev's part of J5; the app's real `/api/fetch` is S37.

## Interface

- CLI (fixed; S37's J5 calls it): `watane-dev new [<slug>] --from <link> [--home <path>] --json`,
  `watane-dev add --release <link or ReleaseRef> [--home <path>] --json`; results as 2.4.
- Takes from app (fixed, app 8.3): `POST /api/fetch` `{"link"}` or `{"release"}`;
  200 octet-stream with `Watane-Release` and `Watane-Package` headers.
- Takes from app (fixed, app 8.1): publish answer `providers: [{"provider", "listed"}]`.
- New module `src/build_on.rs` (TECHNICAL 1). Use pkg's `Package`, `PackageId`,
  `ReleaseRef`, `Link`, `Deps`, `Mod`, `add_provider`; do not redefine them.
  `Link` lives in dist, which dev must not depend on: dev reads only the key
  (between `watane:` and the first `@`) and the slug (after the last `#`) of a
  link text, to check `Watane-Release` (10.1); the app validates the link (its 400).
  Write that rule into 10.1.
