Slice: S50a — Installing watane designed. Docs only.

## Goal
A reviewer can build S50b ("a person can install watane") from the documents alone. Today no
spec says how watane reaches a machine. After this task a new subsystem folder `install/` holds
VISION, FUNCTIONAL and TECHNICAL (and an AGENTS.md like the other subsystems'), and the root specs
place it. The human decided (2026-11-18, factory/PLAN.md S50a): one `curl … | sh` from GitHub
Releases puts `watane`, `watane-dev` and `watane-node` in `~/.local/bin` and `watane.app` in
`~/Applications`, then gives the Gatekeeper step (unsigned: there is no Apple Developer account,
decided 2026-11-15; as few and as calm steps as macOS allows). It offers, y/N and never silently,
to install rustup and the `wasm32-wasip2` target. dev keeps DEV-F-13: dev itself installs nothing.
Every question these decisions leave open is decided in the documents, or listed under
`install/TECHNICAL.md` "Questions" with options, a recommendation and the cost to undo each.

## Acceptance
- AC1 `install/VISION.md`: why it exists, for whom (Alice on a Mac with no Rust; a maker's coding
  agent), what it never does (no silent toolchain install, no root/sudo, no account, no telemetry,
  no auto-update running behind the person's back), and success.
- AC2 `install/FUNCTIONAL.md`: requirements as EARS rules with ids `INST-F-n`, each tracing to a
  root requirement or journey; scenarios `INST-S-n`, each with a literal oracle a test can check
  (exact files that exist after, exit status, what is printed or asked). Cover at least: a fresh
  install on a clean Mac; the toolchain offer answered y, N, and with no terminal (piped, no tty:
  the answer is N and the commands are printed); a checksum mismatch (nothing is installed, the
  partial download is removed); a re-run over an installed version (upgrade); an uninstall;
  `~/.local/bin` not on `PATH` (the line to add is printed, no shell file edited unless the
  document decides otherwise); an unsupported platform (clear stop); `watane-dev new` working
  straight after, given the toolchain.
- AC3 `install/TECHNICAL.md` gives, each exact enough to build: the script (where it is served,
  its name, its flags and environment variables, each step in order, what it prints, its exit
  codes, POSIX `sh` only, the tools it may rely on on stock macOS); the release archive layout per
  platform (file names with version and target triple, the tree inside, including every file a
  program needs beside it at run time; read the code, e.g. `dev/src/allowlist.rs` `vendor_dir`
  looks in `../share/watane-dev/vendor` next to the binary, `dev/src/preview.rs` finds `watane`
  next to `watane-dev`); the checksums file and how the script verifies it, and what that check
  does and does not protect against; the Gatekeeper step (the exact text and command, e.g.
  quarantine removal, and why); the release workflow (`.github/workflows/<name>.yml`: trigger,
  runners, build steps, how `watane.app` is bundled given `app/tauri.conf.json` has
  `bundle.active: false`, upload); version reporting (how a person learns which version they
  have); upgrade; uninstall (what is removed, what is kept: the watane home is never deleted
  without a question); Linux (TC-7, second) either designed or stated out of scope with the
  reason; a test plan; a build-plan table (stages sized for slices, S50b first) that says, for
  each stage, which subsystem folders it touches.
- AC4 The S50b test: where a clean Mac comes from (a second macOS user, a VM, or a CI macOS
  runner; pick one, give the others as options), and what proves "no cargo, no target, no
  checkout" (e.g. a run with a `PATH` and `HOME` that hold none, checked by an assertion, not by
  trust). Which parts run in this repo's `cargo test` (e.g. the script against a local file server
  and a fake archive) and which only on the clean machine.
- AC5 Security: the trust in the download is stated (TLS to GitHub plus the checksum from the
  same release, or more), and `spec/TECHNICAL.md` section 6 gets an "Install" row only if the
  design adds a real boundary; the "Not protected" list names what it does not protect against.
- AC6 `spec/FUNCTIONAL.md` gains a journey line (or requirement) for installing watane;
  `spec/TECHNICAL.md` places `install` in section 2 (table, what it owns: a script, a workflow and
  docs, no crate unless the design needs one, and then say why), and section 8 or 9 says where it
  is designed; root `AGENTS.md` lists `install` in the "One subsystem" cell.
- AC7 `install/TECHNICAL.md` "Questions" lists each open question with options, a
  recommendation and the cost to undo each; "Decisions" lists each decision this task made.
- AC8 Every name used across documents (file names, flags, ids, paths) is the same in each; no
  existing requirement is contradicted (DEV-F-13 holds; F-MAKE-6 holds).
