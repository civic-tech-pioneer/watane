## Goal
App stage F: the app builds and every app test passes on Linux under `xvfb-run`. One script,
`app/scripts/linux-test.sh`, builds a Docker image (Debian, arm64 on this Mac; WebKitGTK 4.1,
GTK 3, Xvfb, the Rust toolchain) from `app/linux.Dockerfile` and runs in it, with the repository
mounted, `cargo test -p watane-app` and `cargo test -p watane-app --features driver -- --include-ignored`
minus the front tests, all green. Linux-only gaps in the app (macOS `cfg` code, the driver's
Linux side, WebKitGTK behaviour) are fixed in the app; facts that differ from macOS are recorded
in `app/NOTES.md`. If WebKitGTK does not resolve `http://<local>.localhost`, that is a finding
in `NOTES.md` with the evidence (and the cheapest app-side fix, if one exists, applied).

## Acceptance
- AC1 `app/scripts/linux-test.sh` (no arguments, run from anywhere) builds the image and runs both
  commands above inside it; it exits 0 only if both pass, and non-zero otherwise. Extra arguments
  are passed to both `cargo test` runs (for example a test name filter). Cargo's registry and the
  Linux `target/` live in named Docker volumes, not in the worktree's `target/` (the macOS build
  must not be clobbered, and a second run must not rebuild everything).
- AC2 In that container: all non-GUI tests pass; every quiet window test (`gui_shell`,
  `gui_isolation`, `support_selftest`) passes; journey `j2` (`slow: journey J2`) passes. Front
  tests (`#[ignore = "front: ..."]`) compile on Linux and are not run by the script (skip them by
  name filter or attribute, documented in the script).
- AC3 The macOS-only parts stay macOS-only and the Linux side is honest: `screen` reports
  `accessory: false` on Linux (TECHNICAL 10); a test that asserts the Accessory policy or another
  AppKit fact asserts it on macOS and asserts the Linux value on Linux (no test silently skips a
  check on macOS). `cargo test -p watane-app --features driver --no-run` and clippy still pass on
  macOS.
- AC4 Hidden windows on Linux: if a hidden (`visible(false)`) WebKitGTK window does not load its
  page, answer `eval` or fire timers, record the observation in `NOTES.md`; change the test's mode
  only with that recorded reason (as S14 did for macOS), never weaken an oracle.
- AC5 `*.localhost`: the isolation and J2 tests open mod pages at `http://<local>.localhost:<port>`.
  Record in `NOTES.md` whether WebKitGTK resolves them on this image (with glib/libsoup versions),
  and on both loopbacks if the test exercises both.
- AC6 `app/TECHNICAL.md` 11 says how to run the Linux suite (the script), and 12 stage F says
  arm64 Linux in Docker is the stage's platform (deputy decision; x86_64 only if arm64 hides a gap).

Docker: try `app/scripts/linux-test.sh` yourself. If your sandbox cannot reach the Docker daemon,
make everything compile on macOS, write the script and Dockerfile, and say under QUESTIONS that
the validator runs it. The validator has Docker.

## Interface
None with a sibling. Keeps the driver protocol of TECHNICAL 10 and the constructors of 11 unchanged.
S18-2 runs beside you and changes `tools_list` (`src/core.rs`, `src/commands.rs`, `ui/app.js`)
and one `j2.rs` assertion in the S11 step; avoid those lines.

## Files
`app/linux.Dockerfile`, `app/scripts/linux-test.sh`, `app/src/**` (Linux `cfg` code, `driver.rs`,
`lib.rs`, `views.rs`), `app/tests/**`, `app/Cargo.toml` (Linux-only dependencies if needed),
`Cargo.lock`, `app/NOTES.md`, `app/TECHNICAL.md` 10 to 12. Not `host/`, not `dev/`, not `pkg/`:
if a test proves a host bug on Linux, stop and report it under QUESTIONS.
