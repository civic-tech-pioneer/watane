## Goal
Three pkg leftovers, re-checked against main on 2026-11-14 (all still as the ledger says).

(1) Safety, the one with teeth. `add_provider` (`src/add.rs`) is the last place in pkg with the
check-then-use gap S22 and S46 closed elsewhere: `directory()` lstats `root.join(relative)` and then
`fs::read_dir`, `fs::create_dir_all`, `fs::write` and `fs::remove_dir_all` act on the same path
string (add.rs:9-26, 35, 55-61, 113-116). A link swapped in after the check is followed: the
consumer's `wit/deps` or `wit/deps/<slug>` replaced by a link to an outside folder after preflight
makes add_provider write WIT files outside the mod. After this task every read and every write of
add_provider goes through the no-follow handle walk of `src/open.rs` (S46): directories are opened
with `open::dir`, listed with `open::entries`, files read through `read_file`, and the consumer's
destination directories are opened once during preflight and written relative to those handles.

Decided here (not by you):
- Add to `src/open.rs` the fd-relative write helpers add_provider needs, Unix via `rustix`
  (`mkdirat` mode 0755, `openat` with `CREAT | EXCL | NOFOLLOW | WRONLY | CLOEXEC` mode 0644,
  `unlinkat` / `unlinkat(REMOVEDIR)` for removing `wit/deps/<slug>`'s old contents through a handle
  walk that never follows a link). Non-Unix keeps path-based fallbacks, as open.rs does today.
- Open the consumer's `wit/deps` handle (creating `wit` and `wit/deps` with `mkdirat` when absent)
  during preflight, before the "Finish all conflict and input checks" point; every later write is
  relative to it or to a handle opened from it. A part that is a link at open time is the existing
  `path` violation at that part (keep "expected a directory without symbolic links" there, file =
  the part's relative path, as today).
- Replacing `wit/deps/<slug>`: remove its old entries through its handle (a link inside is unlinked,
  never followed), then write the new files; or create it if absent. Do not `remove_dir_all` a path.
- Test hook: a `#[cfg(test)]` hook in add.rs (e.g. a thread-local `Option<Box<dyn FnOnce()>>`),
  called exactly once, after preflight and before the first write. Write the swap test first,
  insert the hook into today's code at add.rs:112, and see the test fail (it writes outside); keep
  the hook at the same semantic point in the new code. Report that red run in your report.

(2) An error during a mid-read swap is plain I/O text with no rule (`src/folder.rs`:110, 200, 275
fall through to `ModError::Io`). After this task: in the walks of `links_below` (200) and `inspect`
(275), an entry that was listed and then is gone (`NotFound`) or no longer a directory
(`NotADirectory`) when opened gives a `path` violation at that entry with the message
`changed while the mod was read; read it again`. In `read_file` (110), an open refused because the
entry is a socket (Linux `ENXIO`, macOS `EOPNOTSUPP`) gives the existing `expected a regular file`
(rule = the caller's rule), not I/O text. Other I/O errors (e.g. permission denied) stay `Io`.

(3) `Mod::read` and `pack` word the same link or FIFO differently (folder.rs:92, 217 vs
package.rs:24, 298). After this task both use the same cause and next step, from shared constants
(one module, `pub(crate)`):
- a link where a file or directory may stand: `a symbolic link; replace it with a regular file or directory`
- a link where only a file may stand (mod.toml, deps.json, logic.wasm, `read_file`): `a symbolic link; replace it with a regular file`
- a FIFO, socket or device: `not a regular file or a directory (a FIFO, socket or device); replace or remove it`
`Mod::read` uses these as the violation message (rule `path`, file = the entry). `PackageError::Symlink`
displays ``"`<path>`: " + <link text>`` and the special-file case at package.rs:298 (and 426 if it
is the same case) uses the special text as its reason. `PackageError`'s variants keep their shapes.
