Subsystem: host
Effort: high
Slice: S3 — An edit keeps the data: the agent changes the counter's logic and page while Alice has it open; `serve` again shows the new revision with the same count, and the page updates by itself when the count changes.

## Goal
A mod's page hears from its mod. Outlet imports stop being no-ops: a successful call's events go
to the emitter's own pages, followed by `{"type":"changed"}` when its state changed. Each mod
origin answers `GET /events` with a server-sent event stream of these messages. Installing a
changed build of an installed mod keeps its state (by identity) and sends `{"type":"reload"}` to
its pages. Alice's two open counter pages both see the count go up when she clicks Add in one.

## Acceptance
- AC1 (FUNCTIONAL S13) With `counter` installed and a client reading `GET /events` on
  `http://counter.localhost:<port>` (`Origin` absent): after `/call` `api.add` answers
  `{"value":1}`, the stream gives, in this order,
  `data: {"type":"event","from":"counter","interface":"mods:counter/changes@0.1.0","function":"counted","args":{"count":1}}`
  then `data: {"type":"changed"}` (each message `data: <json>\n\n`; compare parsed JSON with
  literals). After `api.get`, nothing within 500 ms.
- AC2 Order: three `api.add` give three `counted` events with counts 1, 2, 3 in that order, each
  followed by its `changed`. `api.add-then-fail` sends nothing (a failed call emits nothing and
  changes nothing) within 500 ms.
- AC3 Fan-out: two `/events` streams on `counter` both receive the same messages. A stream on
  another mod's origin (e.g. `echo`) receives none of `counter`'s.
- AC4 Update keeps state (FUNCTIONAL S23, without the app part): count `counter` to 2; copy the
  fixture folder to a temp dir, change `ui/index.html`, install it (`install_folders`, and once
  through `POST /api/install`): the answer is the same local `counter`, `GET /` returns the new
  bytes, `api.get` returns 2, and an open `/events` stream receives `data: {"type":"reload"}`.
  Installing the same folder again (unchanged) sends no reload.
- AC5 `/events` headers: 200, `Content-Type: text/event-stream`, and every header of 8.3 (literal
  strings). An `Origin` that is not exactly the mod origin → 403 `forbidden`. A mod origin of a mod
  that is not installed → 404. `POST /events` → 405.
- AC6 Lag: a receiver that falls behind on the bus gets one `{"type":"changed"}` in place of the
  lost messages (unit test on the bus/stream adapter with a small capacity is fine).
- AC7 Keep-alive: `: ping\n\n` after 15 s without a message (a unit test on the stream with the
  interval as a parameter is fine; the program uses 15 s).
- AC8 The program: `watane --preview D --install <counter fixture>`, then an `/events` stream and a
  `/call` `api.add` on its page origin give the `counted` event (one test through
  `env!("CARGO_BIN_EXE_watane")`).
- AC9 `cargo test`, clippy `-D warnings`, `cargo fmt --check` pass. Existing tests stay green. No
  new dependency unless tokio/axum features (`sse`, `sync`, `tokio-stream` is NOT needed: build the
  stream with `axum::response::sse` and `tokio::sync::broadcast` directly, or add
  `tokio-stream` 0.1 with feature `sync` only if axum's API needs a `Stream` you cannot write in a
  few lines; say which in your report).

## Interface
Provides, fixed (dev's template and user-sim rely on them):
- The `/events` wire format of 8.4 exactly: `data: <json>\n\n` messages `{"type":"changed"}`,
  `{"type":"reload"}`, `{"type":"event","from":"<emitter local>","interface":"<full outlet name, with version>","function":"<name>","args":{<param name>: <6.9 JSON>}}`;
  `: ping\n\n` keep-alive.
- `watane.js` and `WATANE_JS` unchanged.
- `Host::call` / `call_async` signatures unchanged; they now deliver to pages before returning.

## Decisions already made (foreman)
- Delivery in this slice goes only to the emitter's own pages (9.2 step 3) and the `changed`
  messages (step 6). Subscribers (steps 4 and 5) wait for links: no mod has subscription links yet
  (install refuses them). Write the loop so step 4 slots in, but do not build it. Mark it
  `// ponytail: subscribers join with links (step 2)`.
- The page bus lives in `Host` (one broadcast channel, capacity 1024) so `call` (no server needed)
  and the server share it; a call with no server running just sends into an empty channel.
- An update is any install whose package id differs from the installed one for the identity; it
  sends `reload` after the catalog commit. If an update today loses state or the local name, fix it.
- Remove the `ponytail: events land in S3` no-op and the S2 cut sentence about it in 15; add a
  short "S3 cut" paragraph to 15 listing what this slice leaves out.
