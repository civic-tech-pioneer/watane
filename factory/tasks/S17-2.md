Slice: S17 — The simplest tool to start with: a maker's coding agent (Claude or Codex, sandboxed or not) gets from an empty folder to a served mod with fewer commands and fewer errors, without reading watane's source.

## Goal
The template `AGENTS.md` that `watane-dev new` writes answers the questions S16's Codex had to
search the web or read watane's source for: how to get the crate allowlist when it is missing
(also from inside a sandbox), how to try the served page without a browser, and how to give the
agent the preview's MCP tools (url and bearer token, which change with each new preview) in
Claude Code and in Codex, including the tool-approval setting each harness needs. It stays
short and plain: an agent reads it whole before it starts.

## Acceptance
- AC1 Missing allowlist: "Order of work" says that when doctor reports `env.allowlist`, run its
  `fix` as given; the fix fills a folder dev finds on its own (no variable to export), and works
  without write access to the watane checkout.
- AC2 Try the page without a browser: a section shows a `curl` call of the page's `/call`, with
  the values the agent has from `serve --json` (`result.pages[i].url` is the origin):
  `curl -s -X POST <page url>call -H 'Origin: <page url without the trailing />'
  -H 'Content-Type: application/json' -d '{"fn":"<iface>.<fn>","args":{...}}'` returning
  `{"value": ...}` or `{"error": {...}}` (host TECHNICAL 8.2). One line says a headless browser
  may hang on the page's open `/events`, so `curl` is the way to check calls; the page's look
  is for the person.
- AC3 MCP tools: a section says that `serve --json` gives `result.mcp.url` and
  `result.mcp.token`, sent as `Authorization: Bearer <token>`; that the token changes when a
  new preview starts (after `serve --stop`, or a restart), so the config must be updated then;
  and gives, for each harness:
  - Claude Code: `claude mcp add --transport http <slug> <mcp url> --header "Authorization: Bearer <token>"`;
    a headless `claude -p` run needs the tools allowed (`--allowedTools "mcp__<slug>"`), an
    interactive one asks the person once.
  - Codex: in `$CODEX_HOME/config.toml` (default `~/.codex/config.toml`)
    `[mcp_servers.<name with _ for ->]`, `url = "<mcp url>"`,
    `http_headers = { Authorization = "Bearer <token>" }`, and
    `default_tools_approval_mode = "approve"` in the same table: without it `codex exec` refuses
    every tool call ("requires approval"), and Codex will not change its own approval setting,
    so the person adds that line.
  - Any other harness: an HTTP (streamable) MCP server with that url and header; if it asks
    before each tool call, the person allows the server's tools.
  Check the Codex keys against the S16 logs in the main checkout
  (`factory/runs/s16-bob/s2.jsonl`, `p*.txt`) and `factory/harness-codex.md`; if a key name there
  differs from the above, use the one that worked and say so in your report.
- AC4 The guide stays readable: `template/AGENTS.md` grows by at most 45 lines; no section
  repeats another. `{{slug}}` placeholders are used where the slug appears, as elsewhere in the
  file.
- AC5 A unit test in `template.rs` (beside the existing AGENTS.md checks) asserts the rendered
  guide holds the literal markers: `default_tools_approval_mode = "approve"`,
  `claude mcp add --transport http`, `Authorization: Bearer`, `curl -s -X POST`, and the
  rendered slug in the MCP examples (no `{{slug}}` left). Existing template tests stay green
  (a test that asserted the old text changes with it; name it in your report).
- AC6 `cargo test -p watane-dev` default run passes; clippy and fmt pass. One spec-gap line in
  `dev/AGENTS.md`; update TECHNICAL 4.1 (template contents) only if it quotes the guide.

## Interface
From S17-1 (built beside you): the `env.allowlist` fix is one command
`'<abs dev>/scripts/vendor.sh' '<folder>'` and dev finds `<cache>/vendor` without a variable;
do not quote the exact paths. The serve result shape does not change.
