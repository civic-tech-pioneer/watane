## Goal

This task closes the adversary's round-4 breach and the prune RISK of the same class (BLOCKED S105,
14d2bcf). dist cannot tell a link the participant gave from a link built out of a record's own
base (a hit's link, `Fetched.link`). fix3 made a base the record *holds* stay unknown, but two
routes make a held base look new again:
1. r4: the 4-base cap evicts the unknown base; a stale hit install then counts it as new and gives it.
2. RISK: after `unfollow`, `prune_listed` removes the record; a kept hit link then creates a fresh
   record with that base given.

Deputy decision, option B (dist only): every record keeps `seen`, each base it ever held, across
eviction and as a tombstone after prune; a link at a seen base that was never given gives nothing.
The rule is written in dist/TECHNICAL.md 4.4 and DD-48 (already committed with this brief): follow
it exactly. Option A (derived links never give, a dist<->app change) is a later slice: touch
nothing under app/.

## Interface

No public signature change. Private: `Follow.seen: Vec<String>` (serde default, skip if empty);
`Follows.seen: BTreeMap<String, Tombstone>` with `Tombstone { seen: Vec<String>, given: Vec<String>, at: u64 }`
(serde default, skip if empty). One helper decides "this link gives its base"
(`!seen.contains(base) || given.contains(base)`), used by `learn_base`, `adopt_given_base`, the
new-record paths of `follow` and `choose_index`, and `held_ungiven` (first read listed). Every
place that adds a base to `base`/`bases` (also `sync_listed`, `holder.rs`) adds it to `seen`.
`learn_base` no longer drops `given` entries that are not held.
