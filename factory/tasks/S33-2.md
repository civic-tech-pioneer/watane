## Goal
Four leftovers from S30 and S31 user-sims, all in dev. After this task: every path dev prints in
`next`, `dir` or `result.home` is the resolved one, whether the home came from `--home` or the
default (macOS: `/private/tmp/...`, not `/tmp/...`); an app error from `search` (503 or any status
without its own fix) gets a fix that names the watane app instead of "Correct the reported host
error"; `search --help` no longer lists `--dir`; and the cause of a fake-app publish taking about
30 s (close to `--wait 30`) is found and, if it is dev's (client or `fake-watane`), fixed.

## Acceptance
- AC1 Paths: with the home given as a path through a symlink (e.g. `/tmp/x` on macOS, or a symlink
  made in the test), and again with the default home (`WATANE_HOME` or whatever
  `watane_host::default_home` reads, pointing through the same symlink), the `next` of an
  `install`/`publish` that finds no running app, `dir` of a `publish` `version_exists` rerun, and
  `result.home` all show the canonical path, identical for both runs. A home that does not exist
  yet is made absolute with its existing ancestor resolved (so `/tmp/new` -> `/private/tmp/new`).
- AC2 `search` against `fake-watane` answering 503 (and against one answering 500 with an app error
  body): exit class and code as today; the fix names the watane app, e.g. "The watane app could not
  search right now; ask the person to check the watane app, then run search again". The same
  generic fix elsewhere in `api.rs` (publish, install, releases) also names the app instead of
  "the reported host error"; keep the 400/declined fixes as they are.
- AC3 `watane-dev search --help` output does not contain `--dir`; `watane-dev search --dir x foo`
  is a usage error (exit class usage), or, if hiding a global flag per subcommand is not possible
  in clap without restructuring, search accepts and ignores it but `--help` still omits it. Every
  other command's `--help` still lists `--dir`.
- AC4 Publish timing: measure `watane-dev publish --json` against `fake-watane` for an accepted
  publish; it completes in under 5 s (a test asserts the bound). If the 30 s comes from the client
  waiting on a connection that is not closed, a missing `Content-Length`, a poll interval, or
  `fake-watane`'s own delay, fix it. If the cause is outside dev, leave it and write the cause in
  the commit message.
- AC5 Tests: unit tests in `dev/src/api.rs`/`dev/src/cli.rs` where they can show it; CLI tests in
  `dev/tests/search.rs`, `dev/tests/publish.rs`, `dev/tests/install.rs`. `cargo test -p watane-dev`
  (and `-- --include-ignored` with `WATANE_BIN` set), clippy `--all-targets --all-features -D
  warnings`, `cargo fmt --check` pass.
