# app: technical specification

How the app does what `FUNCTIONAL.md` says. Steps 2 to 4 are built.
Step 5 (stage E) is designed (S32) and not built. Step 8 (stage G, own
machines) is designed (S59) in sections 3, 6.2, 7, 8 and 9.8.

## 1. Crate and layout

One crate at the root of this folder: package `watane-app`, lib `watane_app`,
binary `watane-app`. Tauri 2. The app's own interface is plain HTML, CSS and
JavaScript modules in `ui/`, with no framework and no build step.


## 3. Process and startup

One process holds the Tauri event loop, the host, dist and the server.
Tauri's async runtime (tokio) runs the server and the async calls. `Dist`
blocks: every dist call runs in `tauri::async_runtime::spawn_blocking`.

`run(config)` does, in this order:

1. Create the `Broker` (section 6) and an empty parties cache (9.2).
2. `Host::open(home, Mode::Home { app: Some(Arc::new(HostConfirm { broker,
   parties })) }, Limits::default())`. It is first because it refuses a
   non-empty home without `home.json` (host 3.1).
3. Create `<home>/app/` if missing. Read or create the mark (section 6.4).
4. `Dist::open(home, Arc::new(DistConfirm { broker, parties }), Options::default())`
   (stage C). It creates the identity at the first open, offline
   (APP-F-28). From stage G: `Node::open(home, Arc::new(DistConfirm {
   broker, parties }), options)` in its place, where `options` is
   `watane_node::Options::default()` with `net.on` true, so that `net`
   takes its switches from `book.json` (node 5.6, node Q1); it
   opens the home keyless when it is a replica (node 5.6), and
   `Core.dist` is `node.dist().clone()`.
5. Build Tauri: `tauri_plugin_dialog::init()`, `manage(AppState)`,
   `invoke_handler(generate_handler![<the commands of section 7>])`.
6. In `setup`:
   1. Make the `Core`. `tauri::async_runtime::block_on(host.serve(port,
      api::router(Some(dist.clone()))))` gives the `Served`; keep it in `Core.served`.
   2. `broker.set_listener(...)`: on each change of the head request, close
      the consent window and, if a request remains, open a new one.
   3. Fill the parties cache (section 9.2). Build the menu and open the
      first window (5.4; stage I). Before stage I: open the main window.
   4. Start the refresh loop (stage C, section 9.5). Stage G: start the
      machines thread (9.8).
   5. With feature `driver`: start the driver.
   If step 2, 3, 4 or 6.1 fails, set `AppState.failed`, skip the other
   steps except opening the main window, and serve nothing (APP-F-2). The
   main window then shows only the cause. A serve `PortInUse(P)` uses
   `words::port_in_use(P)` in `status.error` and the main text, and prints
   that same line to stderr once. No server means no `run.json`. Other
   serve failures retain `cause_chain` text.
7. On `RunEvent::ExitRequested`: `broker.deny_all()`. On `RunEvent::Exit`:
   `block_on(served.shutdown())`. Closing the main window exits the app;
   from stage I, closing the last window other than `consent` does
   (APP-F-64).

```rust
pub(crate) struct AppState {
    pub home: PathBuf,
    pub mark: OnceLock<String>,        // set in step 3
    pub broker: Arc<Broker>,
    pub core: OnceLock<Arc<Core>>,     // set in step 6.1
    pub failed: OnceLock<String>,      // the cause of APP-F-2
}
pub(crate) struct Core {
    pub host: Arc<watane_host::Host>,
    pub dist: Arc<watane_dist::Dist>,                // stage C
    pub node: Arc<watane_node::Node>,                // stage G: every call with a net side (9.8)
    pub machines: Arc<Machines>,                     // stage G: what the machines view shows (9.8)
    pub broker: Arc<Broker>,
    pub parties: Arc<Parties>,                       // section 9.2
    pub served: std::sync::Mutex<Option<watane_host::Served>>, // port, page_url, mcp_url
    pub app: tauri::AppHandle,
    failures: std::sync::Mutex<BTreeMap<String, String>>, // last failed refresh by channel
}
```

`<home>/app/` belongs to the app; host reserves it. It holds only `mark`, `main` (stage I, 5.4), `mod-webview-context/` (the mod
views' context key, 5.1; WebKit may create files there) (and `fetched/` in
step 5). dist keeps the site folder in `<home>/dist/site/`.

## 4. Grant words

This closes "the words of each grant in the consent view" (spec/TECHNICAL.md
section 9, step 2). `words::grant_line` renders each `Grant` of `pkg`:

| Grant | `kind` | `text` |
|---|---|---|
| storage | `storage` | `Keep its own data on this device` |
| network, host `{host}` | `http` | `Connect to {host}` |
| call of `{interface}` from `{provider}` | `call` | `Call {interface} of {provider}` |
| subscription to `{interface}` of `{provider}` | `subscribe` | `Receive the {interface} events of {provider}`; from step 9 `Receive the {interface} events of {provider} and answer its requests`, because one subscription also answers its collects (W34) |

- `{host}` is the host name as `mod.toml` writes it.
- `{interface}` is the interface as `pkg` writes it, for example
  `mods:reading-list/books@0.1.0`.
- `{provider}` is `<slug> (local)` for a local provider and
  `<slug> by <party>` for a published one (pkg names a provider by slug and
  publisher, PKG-F-7).
- `<party>` is `you` for the own key; otherwise `<profile name> (<fingerprint>)` when the parties cache
  knows a name, else `<fingerprint>`. The fingerprint is
  `PublicKey::fingerprint` (log, through dist); before stage C it is the
  first 10 characters of the key text.
- Step 5: when a bind of the mod names the grant's provider (host 4.5),
  `{provider}` is the bound mod, followed by ` (in place of <the pinned
  provider>)`; the same holds for the `uses` lines. So the words name the
  mod that the call reaches.
- `GrantLine.key` is pkg's stable text form of the grant (PKG-F-19), for
  example `call mods:reading-list/books@0.1.0 from local/reading-list`.

- **Short form** (W37, the details of 5.3 only). `GrantLine.short` is the
  same sentence in plain words: `{interface}` is the interface's name
  without namespace, package and version (`books` for
  `mods:reading-list/books@0.1.0`), and `{provider}` is the provider's
  installed mod name (else its slug) followed by ` by <party name>` (the
  profile name, else the fingerprint; `you` for the own key) or
  ` (local)`. A bound provider keeps ` (in place of <name>)`. Storage,
  network and manage lines are the same in both forms. A subscription to
  an interface named `events` reads `Receive the events of {provider}`
  (not `the events events`). Example:
  `Call books of Reading list by Alice`. The consent view and every request
  show only `text`; `short` never replaces it there, because the
  participant decides on the exact words. `GrantLine.short` is
  `#[serde(default)]`; an empty `short` renders `text`.

```rust
pub fn grant_line(grant: &Grant, parties: &Parties, granted: bool, new: bool) -> GrantLine;
// W37: grant_line leaves `short` empty; Core sets it with grant_short for ModView.grants and
// ModView.offerGrants. names: installed mod names by provider identity (<publisher>/<slug> or local/<slug>),
// so a bind can name two providers of the same slug from different publishers.
pub fn grant_short(grant: &Grant, parties: &Parties, names: &BTreeMap<String, String>) -> String;
// step 5: grant_line_bound(grant, binds: &[Bind], parties, granted, new); grant_line is it with no binds
pub fn party(publisher: &str, parties: &Parties) -> Party;
```

## 5. Windows

| Label | URL | Content |
|---|---|---|
| `main` | `tauri://localhost/index.html` | the manager (library, find, updates, details) and, from stage I, settings (identity, site, backup, agents, machines) |
| `consent` | `tauri://localhost/consent.html` | one request at a time |
| `mod-<local name>` | `InstalledMod.page` (`Served::page_url`) | one mod page |

The app creates every window in code (`app.windows` is empty).

### 5.1 Mod windows

`views::open_mod(app, local, page, title)`:

- If the label exists: `set_focus()` unless a consent request is open, then return (APP-F-7, APP-F-14).
- Else `WebviewWindowBuilder::new(app, "mod-<local>", WebviewUrl::External(page))` with:
  - `.title("<mod name> — <party or 'local'>")` (APP-F-6). Never register
    `on_document_title_changed`.
  - `.incognito(true)`: a new non-persistent store for each window
    (APP-F-10; the colos probe showed one store per webview on macOS).
  - `.data_directory(<home>/app/mod-webview-context)`: a separate context key, so tauri-runtime-wry's once-per-key Linux protocol registration does not consume main/consent's default key; mod storage stays ephemeral, though the unused bookkeeping context creates WebKit files there (NOTES S85).
  - `.on_navigation(|u| u.origin() == page.origin())`; record each refusal.
  - `.on_new_window(|_, _| NewWindowResponse::Deny)`; record it.
  - `.on_download(|_, _| false)`; record it.
  - `.disable_drag_drop_handler()`: the page gets plain HTML drag and drop;
    Tauri sends no file path.
  - `.inner_size(900.0, 680.0)`. Never `always_on_top`.
- `views::close_mod(app, local)` closes the window if it exists. Core calls
  it before `host.disable` and `host.remove` (APP-F-11). A removal of the
  files does not stop an open page (colos finding), so the close is needed.

A local name is a DNS label of 1 to 24 bytes (host 3.2), so `mod-<local>`
is a valid Tauri label.

### 5.2 Consent window

Opened by the broker listener for the head request:

```rust
WebviewWindowBuilder::new(app, "consent", WebviewUrl::App("consent.html".into()))
```

### 5.3 Main window

`tauri://localhost/index.html`, 1000 × 700, title `watane`. One page with
the views launcher, details, agents (toolsets and tokens) and, from stage C,
identity and channels, and from stage D, find. It never shows mod content.

From stage I the page has two areas, chosen by the hash `#mods` (default)
or `#settings`:

- **Mods** (the manager): the views Library, Find and Updates, and the
  details of one mod. From W37 they look as the human's design draws them
  (5.3.1 to 5.3.7). The window accepts dropped folders (APP-F-20): the
  `main` window keeps Tauri's drag-and-drop handler, and a drop event's
  paths go to `install_paths`.
- **Settings**: identity, site, backup and restore, agents (toolsets and
  tokens) and own machines, as before, in the tokens of 5.3.1. Its header
  holds the title `Settings`, a link `Back to mods` (to `#mods`) and the
  mark. The design has no Settings board.

**The design** (W37) is `spec/design/manager/`: the boards `Main`
(Library and details), `Find`, `Updates`, `Empty` (first start) and
`Shell` (launch with a main mod, the menu), and the launch rule and design
rules in `canvas.json`. The boards are HTML mockups with sample data: read
them for layout, sizes, colours and words, never as code to copy. Where a
board and an APP-F rule or this section disagree, the rule wins and this
section says so ("rule wins"). The demo's findings are
`COMPARISON-2026-11-16.md` beside them. Design rules that hold in every
view: two levels (a list, then one mod); one primary action per view (per
card where a view is a list of cards);
a destructive action is never the default and never focused first; quiet
chrome, so that the consent view stands out.

### 6.1 Broker

```rust
pub struct Broker { /* Mutex<VecDeque<(AskId, Request, oneshot::Sender<Answer>)>>, listener */ }
#[derive(Clone, Debug, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct AskId(String);             // 32 lowercase hex characters from 16 random bytes
#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
#[serde(tag = "answer", rename_all = "snake_case")]
pub enum Answer { Approve { withheld: Vec<Withheld> }, Pick { choice: String }, Deny }   // Pick: step 5
#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
pub struct Withheld { pub local: String, pub key: String }  // PlanMod.local; GrantLine.key
#[derive(Debug, thiserror::Error)]
pub enum ConsentError {
    #[error("this request is no longer open")] Stale,
    #[error("a withheld grant is not in the request: {0}")] UnknownGrant(String),
    #[error("this answer does not fit the request")] WrongAnswer,          // step 5
    #[error("the choice is not in the request: {0}")] UnknownChoice(String), // step 5
}

impl Broker {
    pub fn new() -> Arc<Broker>;
    /// Queues the request and waits for the answer. Dropping the future removes the request.
    pub async fn ask(&self, request: Request) -> Answer;
    /// The same for a blocking caller (dist). Never on the main thread or a tokio worker.
    pub fn ask_blocking(&self, request: Request) -> Answer;
    pub fn current(&self) -> Option<(AskId, Request)>;
    /// Only commands::consent_answer and the Destroyed handler call this.
    pub fn answer(&self, id: &AskId, answer: Answer) -> Result<(), ConsentError>;
    pub fn deny_all(&self);
    /// Called with the new head after each change. One listener.
    pub fn set_listener(&self, f: Box<dyn Fn(Option<AskId>) + Send + Sync>);
}
```

Rules: first in, first out (APP-F-17). `answer` accepts only the id of the
head. `withheld` must be empty for a `Sign` request, and each entry must
name a grant line of that request, else `UnknownGrant`. Step 5: a `Pick`
request takes only `Pick` or `Deny`, and `choice` must equal the `choice`
of one of its candidates (`UnknownChoice`); an `Install` or `Sign` request
takes only `Approve` or `Deny` (`WrongAnswer`). Step 8: a `Join` or
`Reach` request takes only `Approve` with no `withheld`, or `Deny`
(`WrongAnswer`). `deny_all` answers
`Deny` to every open request. A request with no answer 600 s after it was
queued is answered `Deny` and removed (W19; host refuses at the same time,
host 12.1).

Behaviour:

- Arguments `local`, `toolset` (`name`) and `handle` are parsed with
  `LocalName::parse`, `ToolsetName::parse` and `Handle::parse`; host's
  `bad_name` passes through.
- `mod_open`: `host.get(local)`; no mod or no `page` gives `not_found`.
- `install_folders`: `pick_folders` (dialog plugin, Rust API, or the
  driver's `pick`). Cancel gives `{installed: []}`. Then `host.plan` of
  `Source::Folder`s and `host.install(plan, Requester::App).await`; host's
  `missing_providers` and `refused` pass through (APP-F-20, APP-F-21).
- `mod_disable`, `mod_remove`: `views::close_mod` first, then host.
- `install_paths` (I): as `install_folders` with the dropped paths in
  place of the dialog; a path that is not a directory gives `bad_request`.
- `main_set` (I): `null` deletes `<home>/app/main`; a local name of an
  installed mod with a page writes it; else `not_found`.
- `updates_done` (I): the automatic updates of 9.5 that succeeded since
  start, newest first, at most 50; kept in `Core`, not on disk.
- `mod_remove`: the page first asks "Delete the data of <name>?" with the
  buttons `Keep data` (focused) and `Delete data`.
- `grant_withdraw`, `grant_give`: find the `GrantState` of the mod whose
  grant text form is `key`; none gives `not_found`. Then `host.revoke` or
  `host.grant`. No consent view for either: a withdrawal only removes
  authority, and a give-back is the participant's own act in `main`, which
  no mod reaches (host 4.4).
- `tools_list`: for each enabled mod, `host.functions(local)` as rows with `entry`
  `<local>:<interface>.<function>` and `tool` `<local>_<interface>_<function>`
  (short interface name, host 3.2 and 10.1). The page labels each checkbox
  with `tool` and keeps `entry` as its value. Saved toolsets also display
  `tools` returned by `toolsets_list`, derived in Rust by the same function
  as `tool_row`, aligned with `entries`. This includes unavailable or disabled
  mods; a whole-interface entry `<local>:<interface>` reads
  `<local>_<interface>`. The page never derives tool names.
  `toolset_save` still passes the unchanged entry strings to `set_toolset`.
- `toolset_remove(name)`: parse `ToolsetName`, then `host.remove_toolset`;
  unknown names keep the host's `no_toolset` code. Each saved row has a
  `Remove` button with class `remove-toolset`. Refresh removes the row and
  its `#token-toolset` option; the host determines what happens to bound tokens.
- `token_issue`: the page shows the token once with `Served::mcp_url` and a
  copy button, and keeps no copy. `token_end` false gives `not_found`.
- `identity_backup`: a passphrase of at least 12 characters, else
  `bad_input` (the page also checks that two entries are equal). Then
  `save_file` with the default name `watane-identity.backup`, then
  `dist.backup(passphrase)`, then write the file with mode 0600.
- `identity_restore`: `pick_file`, read it, `dist.restore(bytes,
  passphrase)`. dist refuses when the own channel holds a statement
  (APP-F-31). After a restore, the page shows the step of section 9.1.
- Polling: the main page calls `status` and `mods_list` at load, on window
  `focus`, after each action, and every 2 s while visible. The app sends no
  Tauri events.

The pages call commands only through `ui/ipc.js`:
`export const call = (cmd, args = {}) => window.__TAURI_INTERNALS__.invoke(cmd, args);`.

## 8. Local API routes that need dist

The host owns the local API, its guards (host 8.1: the API host names
only; no `Origin` header) and its discovery by `watane-dev` (`run.json`).
The app hands `api::router(Some(dist))` to `host.serve`, which merges it on the
same port behind the same guards (HOST-F-38).

```rust
pub fn router(dist: Option<Arc<watane_dist::Dist>>) -> axum::Router;   // full paths: /api/publish, /api/releases, ...
```

From stage G the router owns a node handle instead,
`router(node: Option<Arc<watane_node::Node>>)`: `/api/publish` calls
`node.publish` (and `node.list` for its providers), `/api/search`
`node.search`, `/api/fetch` `node.read_link`, so that own machines learn
of a new release and a light machine reads through a full one (node 5).
dist's `NoIdentity` maps to 409 `no_identity` on every route (APP-F-50).
No route reaches `node.net()` (APP-F-61).

The router owns only a dist handle, not `Core`: host is not served until
startup succeeds, and this avoids a server/router/Core ownership cycle.
`None` gives the route's 503 response in isolation; failed startup serves
nothing (APP-F-2). Publish-specific errors are mapped by the table;
all other dist errors use its generic 409 row, including new variants.

An error body is `{"error": {"code": "<code>", "message": "<cause chain>"}}`
(D-A5), the same shape as host's.

### 8.1 `POST /api/publish` (step 3)

Request: `Content-Type: application/octet-stream`; the body is the package
bytes. The route sets `DefaultBodyLimit::max(67_108_864)` (dist's package
limit); host's 64 KiB limit must not apply to it (section 15).

In `spawn_blocking`: `dist.publish(bytes)`. dist decodes, checks, asks
`DistConfirm` (the participant sees the `release` request), signs, appends
and writes the site folder.

| Result | Status | Body or code |
|---|---|---|
| published | 200 | `{"release": "<ReleaseRef>", "site": "<site dir>", "link": "<link text>" \| null, "providers": [{"provider": "<key>/<slug>", "listed": bool}]}` (`providers`: step 5, below) |
| wrong content type, empty body, invalid provider link or one without a slug, more than 32 provider links | 400 | `bad_request` |
| body over the limit | 413 | `too_large` |
| `DistError::Refused` | 403 | `refused` |
| `DistError::Package` | 422 | `invalid_package` |
| `DistError::SiteNotWritten` | 500 | `site_not_written`; the release is signed and stored; the message says so |
| `DistError::VersionExists` | 409 | `version_exists`; `release <ref> already exists` (no sequence number) |
| any other `DistError` (an unreleased provider, an unconfirmed own head, ...) | 409 | `publish_refused` |
| dist did not open (APP-F-2) | 503 | `unavailable` |

`link` is `dist.own_link(Some(slug))`; it is `null` while no site URL is
set (`NoSiteUrl`). The route never answers a confirmation: only
`consent_answer` and the `Destroyed` handler call `Broker::answer`
(APP-F-13).

**Providers of another publisher (step 5, W25).** The request may carry
one header `Watane-Provider-Links`: link texts with a slug, separated by
one space, at most 32 (dev sends the links it fetched with, dev 9.7). A
link that does not parse or has no slug, more than 32 links, or repeated
header fields is 400 `bad_request`, before anything is signed. After the release is
signed, for each distinct `(key, slug)` of a `Call` or `Subscribe` grant of
the release whose key is not the own key, in grant order:

1. The own channel has a live `list` of it: `listed: true`.
2. Else the base comes from the header's link with that key and slug, or
   else from a **followed** channel record of that key (never from a
   listed record: its base came from a third party). With a base:
   `dist.list(&Link::new(key, base, Some(slug)), "used by <slug of the
   release>")`. The participant sees the `list` request with its location
   (6.2). `Ok` gives `listed: true`; `Refused` or any other error gives
   `listed: false`.
3. Else `listed: false`.

A header link whose key and slug match no such provider is ignored.

A `false` never fails the publish: the release is signed. It means that a
person who installs it needs a followed channel or an index that names the
provider's base (dist 5.11). dev warns about it (dev 9.7).

For `ModError::Invalid`, the 422 message drops a violation text's leading
file name, which the location already gives, so the file is named once:
`the mod breaks 1 rule(s): [component] logic.wasm: is not a WebAssembly component`.

### 8.1.1 `GET /api/releases` (step 3)

In `spawn_blocking`: read `dist.own().releases` in seq order. Answer 200
`{"releases":[{"slug":string,"version":string,"release":string,"seq":number,"link":string|null}]}`,
one object per own release, including withdrawn releases, with no withdrawal
field yet. An empty channel answers `{"releases":[]}`. Each link comes from
`dist.own_link(Some(&slug))` using the current site URL; `NoSiteUrl` means
`null`. No confirmation is needed. This lets an agent discover a completed
publish before building or after its publish wait expired.

No dist handle gives 503 `unavailable`, with message `dist did not open`.
Other read failures give 500 `unavailable` with the cause. Other methods
return 405, `Allow: GET`, and `method_not_allowed` with message `use GET`, in the common
built-in API routes do (HEAD has no response body).

### 8.2 `POST /api/search` (step 4)

Request: `Content-Type: application/json`,
`{"text": string, "publisher": string|null, "interface": string|null}`
(`text` may be `""`; its limit is dist's `Query`). In `spawn_blocking`:
`dist.search(&Query)`. No consent: a search reads only what the
participant chose to read, and gives no authority. It makes no network
request (dist 5.10), so it never waits on a web host.

| Result | Status | Body or code |
|---|---|---|
| searched | 200 | `{"indexes": <number of chosen indexes, own excluded>, "results": [Result]}` |
| bad JSON, a `publisher` that is no key, an `interface` that is no interface name, `text` over dist's limit | 400 | `bad_request` |
| dist did not open (APP-F-2) | 503 | `unavailable` |
| any other read failure | 500 | `unavailable` with the cause (as 8.1.1) |

```text
Result {release (ReleaseRef), name, summary, link (link text) | null,
        publisher: {key, name: null | string, fingerprint},
        status: "ok" | "compromised", checked_at: null | number, unchecked_since: null | number,
        via: [{kind: "own" | "followed" | "index", index: null | key, through: null | key, note}],
        offers: [string], events: [string], uses: [string],
        origin: null | string}                     // step 5: ReleaseRef text
```

Derived from `dist::Hit` as `HitView` (section 7) is, in snake case, with
these differences: `publisher` always has its `key`; `via.index` and
`via.through` are key texts, not `Party`; no `slug`, `version`, `verified`
or `installed` (the `release` text holds slug and version). `uses` holds
the interfaces of the call and subscribe grants. The route exists for
`watane-dev search` (dev 10).

### 8.3 `POST /api/fetch` (step 5)

Request: `Content-Type: application/json`, either `{"link": "<link
text>"}`, a link **with** a slug, or `{"release": "<ReleaseRef>"}`; not
both. In `spawn_blocking`: for a link, `Link::from_str`, then
`dist.read_link(&link)` (dist 5.11: no follow, no record; a link on a local
address is refused as a listed base is). For a release,
`ReleaseRef::from_str`, then `dist.fetch(&release)` (dist 5.7 and 5.11: a
channel with a record, or one that a stored listing names; no follow). dev
uses the second form for the providers of a provider.
The answer is the package itself, so no file is written and none is left
behind:

| Result | Status | Body or code |
|---|---|---|
| fetched | 200 | `Content-Type: application/octet-stream`; the package bytes; headers `Watane-Release: <ReleaseRef>` and `Watane-Package: <package id>` |
| bad JSON, both or neither field (including both null), a link or release that does not parse, a link with no slug | 400 | `bad_request`; non-JSON or wrong shape reads `give link or release: <serde cause>` using the rejection body text; both/neither fields keep exactly `give link or release` |
| `NoRelease`, `Withdrawn`, `Compromised` | 409 | `fetch_refused` with dist's cause |
| `NotFollowed` (no base known for a release), `BadUrl` (a local address) and any other `DistError` (a read, a hash or a package check failed) | 502 | `fetch_failed` with dist's cause |
| dist did not open (APP-F-2) | 503 | `unavailable` |

A wrong method on any app `/api/*` route answers 405 with
`{"error":{"code":"method_not_allowed","message":"use POST"}}`
(`use GET` for releases), and an `Allow` header. HEAD has no response body,
as HTTP requires.

No consent: a fetch installs nothing, grants nothing, signs nothing and
follows nothing; its only lasting effect is a verified package in dist's
cache and the read entries in `<home>/log/` (dist DD-29). The route sets
`DefaultBodyLimit::max(65_536)` to match host's 64 KiB API limit; the answer is at
most dist's package limit. `watane-dev new --from` and `add --release`
use it (dev 10). The route never answers a confirmation.

### 9.1 Identity and site

- `site_set_url(url)` calls `dist.set_site_url(url)`. `status.site` is

  published". The answer goes to `identity_confirm_own`, which calls

### 9.2 HostConfirm, DistConfirm and the parties cache

```rust
pub(crate) struct Parties { names: RwLock<BTreeMap<String, String>>, own: RwLock<Option<String>> }
pub(crate) struct HostConfirm { pub broker: Arc<Broker>, pub parties: Arc<Parties>, pub host: OnceLock<Weak<Host>> } // impl watane_host::Confirm
pub(crate) struct DistConfirm { pub broker: Arc<Broker>, pub parties: Arc<Parties>, pub dist: OnceLock<Weak<Dist>> } // impl watane_dist::Confirm
```

- The parties cache remembers profile names and the own key (`you`). Core fills
  it at startup and after changes, and before rendering every channel it shows:
  followed/chosen/listed/included/skipped channels, search and pick publishers,
  fetched releases, installed and planned publishers, origins, grant providers
  and bind targets. The API fetch route uses the same cache, so a later
  HostConfirm can name fetched channels without any dist call. `dist.channel(key)` reads the local log only, including for
  channels that are not followed. New reads augment the cache rather than
  dropping an unfollowed fetched channel. HostConfirm only reads this cache;
  it never calls or waits on dist. DistConfirm holds a weak dist reference and
  fills the parties named by its sign request from local channel views before
  asking the broker; no network read or reference cycle is introduced. A
  failed profile read is shown in the sign details with its full cause.
- HostConfirm receives a weak host reference immediately after `Host::open`,
  avoiding a host/confirmation reference cycle while resolving installed providers.
- `HostConfirm::install(InstallRequest { entries, requester })` (also an
  update with new grants) gives `Request::Install` (`by_program` for
  `Requester::LocalApi`), one `PlanMod` per `PlanEntry` in order:
  `replaces` from `Change::Update`, `new` for each of `new_grants`, `uses`
  from `providers` (looked up in `entries`, else `host.get`). It awaits
  `broker.ask`, and maps each `{local, key}` to the `(LocalName, Grant)` of
  `Answer::Approve { withhold }`.
- `DistConfirm` maps `SignRequest` to `Request::Sign` with the details of
  section 6.2 and `signer` from the request's channel and fingerprint. It
  calls `broker.ask_blocking`. It never calls `set_name`, `publish` or
  `withdraw` (dist holds its own lock during the call).

### 9.3 Follow

`channel_follow(link)`: `Link::from_str`, then `dist.follow(&link)`;
`channel_unfollow(key)`: `dist.unfollow`. `channels_list` maps
`dist.followed()` to `ChannelRow`. The status is `compromised` for
`Status::Compromised`, `failed` with the cause of the last
`Outcome::Failed`, else `ok`.

### 9.4 Install from a link

`install_link(link)`:

1. `Link::from_str(link)`; a link with no slug: `dist.follow` it and answer
   `bad_input` "the channel is followed; the link names no mod".
2. `dist.open_link(&link)` gives `Fetched { package, entry, .. }`, as
   `Source::Release { package, entry }` (host 2.4: the typed values, both
   already checked by their decoders).
3. Loop: `host.plan_with(sources, binds)` (`binds` starts empty). For
   each `MissingProvider` of `plan.missing()` with `release: Some(r)`:
   `dist.fetch_for(&r, <key of m.needed_by, None when local>)` (dist
   5.11), and add it to `sources` as in step 2. Step 5: when that fetch
   fails, run the pick of 9.7 with its cause; it adds a source and binds,
   or ends the install. One without a `release` (a local
   provider): `missing_providers`. Stop when nothing is missing. If a
   round adds no source and no bind, or after 32 rounds:
   `missing_providers`.
4. `host.install(plan, Requester::App).await` (the consent view through
   HostConfirm).
5. Step 5: for each `Fetched` of this install (the hit of a pick too) whose `link` is set and whose
   channel is not followed, `dist.follow(&link)` (dist 5.11, DD-29), so
   that a provider's updates and withdrawals keep coming. A failed follow
   does not undo the install; it shows as that channel's failure
   (APP-F-37).

dist and host verify. The app passes their cause through (APP-F-37).

### 9.5 Refresh loop

A tokio task with `interval(600 s)`; the first tick is at once. Each tick
and each `channels_refresh` run `Core::refresh` in `spawn_blocking`, keep
each `Outcome::Failed` cause, map `dist.followed()` to `[ChannelRow]`, and
refill the parties cache. Core also returns one update ReleaseRef per
installed mod whose publisher report contains a `Change::Release` of its
slug above its installed version and whose newest live version is higher
than the installed version.
Compromised channels produce no automatic updates.

Both callers spawn one independent task per update and return without
waiting for installs or consent. Each task fetches the release in
`spawn_blocking`, shares `install_link`'s provider resolution without the
pick of 9.7 (a failed provider fetch is that update's error), and calls
`host.install(plan, Requester::App)`. Host decides whether confirmation is
needed. Errors, including refusal, are retained by local name with the
target version until a successful app install of that mod clears them.
`channels_refresh` still returns `[ChannelRow]`.

For followed published mods, the offer is the highest version of the slug
with no withdrawal, unless already installed; it can be a downgrade.
Notice priority is compromised channel, installed release withdrawal with
reason, then the last update result, then the channel refresh failure as
`Could not read <channel name, else fingerprint>: <cause>` through
`words::index_read`. Host code `refused` becomes
`You declined the update to <version>.`; every other failure remains
`Update to <version> failed: <cause>` with the whole cause. Local mods
and unfollowed publishers have neither notice nor offer. Text comes from
`words.rs`; the launcher renders it through `textContent` and offers
`Install <version>` via `release_install` (bad ReleaseRef: `bad_input`).
`ModView.offerGrants` contains the offered release's `ReleaseInfo.release.grants`
from the followed `ChannelView`, excluding every `Grant` present in
`InstalledMod.grants` (including withheld grants). Each uses
`words::grant_line(grant, parties, false, true)`. No offer gives `[]`.
A nonempty list adds ` — asks for: <text>, <text>` to the offer button
(in the details; from W37 the Updates card shows the grants as chips and
labels the same button `Review…`, 5.3.6).
`ui/words.js` owns the pure `offerLabel(release, grants)` and
`ownWithdrawal(reason)` functions; `app.js` uses them for the offer button
and own withdrawn release row. Default window tests import that module
for the wording and install a real fixture for the version sibling.
This is derived on every read and survives restart; decline notices remain
in memory only. Each launcher entry keeps its name in `h2` and shows
`mod.version` in a sibling with class `version`, outside Details.

`Status.identity.releases` lists `dist.own().releases`. Live releases have a
reason input and `Withdraw` button. A withdrawn own release reads
`Withdrawn: <reason>`; another publisher's installed release remains
`Withdrawn by the publisher: <reason>`. `release_withdraw` parses the reference
(`bad_input` on failure), calls `dist.withdraw` in `spawn_blocking`, and
does no reason validation itself. It maps dist `BadReason { cause }` to
`bad_input` with `words::bad_reason(cause)`: `invalid character count` gives
`Give a reason of 1 to 280 characters.`; every other cause gives
`This reason cannot be used: <cause>.`. Other dist failures and their
causes pass through. DistConfirm handles signing
consent, including the release and withdrawal reason.

### 9.7 Build on (step 5)

**Pick** (F-BUILD-3, APP-F-41). For a `MissingProvider` `m` whose fetch
failed with cause `c`, needed by the plan entry `e`:

1. Needed interfaces: each `Call` or `Subscribe` grant of `e.grants` whose
   provider is `m.provider`.
2. Candidates: `dist.search(&Query { interface: Some(<first needed
   interface without its @version>), .. })`, keeping each hit with status `Ok`, the slug of
   `m.provider`, a publisher other than `m.provider`'s, and, for every
   needed interface `n`, an interface `i` with `n.satisfied_by(i)` in
   `release.offers` (for a call) or `release.events` (for a subscription).
   Hits of installed released mods come through the same search (their
   channels are followed). Local mods are no candidates. At most 20, in
   search order. This is a pre-filter; host checks the fit again (host 4.5).
3. No candidate: `missing_providers` with the message `<provider> is not
   available (<c>), and no mod in your indexes fits in its place`.
4. Else `broker.ask(Request::Pick { consumer: e.name, provider: <{provider}
   of section 4>, cause: c, candidates })`. `Deny` or no answer:
   `refused`. `Pick { choice }`: the candidate's hit. If it is not
   installed, `dist.fetch(&hit.info.reference)` (its channel has a record)
   and add it to `sources`. Add `Bind { consumer, provider: m.provider,
   to: "<choice key>/<slug>" }` to `binds` for **every** plan entry whose
   `deps.json` pins `m.provider`, so one pick serves all its consumers;
   each one shows in the install consent.
5. The plan that follows shows each bind in the install consent
   (`PlanMod.binds`), so the participant confirms the pick with the grants.

The pick and the install are two consent views in a row: the pick says
which mod, the install says what it may do. A background update (9.5)
never opens a pick: the installed binds carry over (host 4.5), and a
provider that is still missing is that update's error.

**Origin** (F-BUILD-1, APP-F-42). `ModView.derivedFrom` is the installed
mod's origin. The details show it as `Made from <name or slug> <version> by
<party> (the publisher says so)`, with the name and party from the
parties cache and dist's view of the origin's channel when stored, else
the ReleaseRef text. The install consent and the `release` sign request
show it too (6.2, 6.3). The confirmation adapter retains the origin
reference at the end after ` — `. It starts with
`<name> <version> by <party label>` when the real host has that release;
otherwise it uses the slug, version and cached party label.
`PlanMod.origin` remains nullable text; no consent command or field is added.

**Derived mods** (F-BUILD-4, APP-F-42). For an installed mod with a
`release`, the details call `search` with `origin` `<publisher>/<slug>`
(`dist.search(&Query { origin: Some((publisher, slug)), .. })`); a local
mod makes no call. A bad `origin` text is `bad_input`. The details
list them as `Made from this: <name> <version> by <party>`, each with the
install button of a hit (`install_release`), or `Installed` with no install
button when already installed. The page says `as far as your
indexes list them` above the list.

### 9.8 Own machines (step 8)

Stage G. The app calls `node` (node 3) for every call with a `net` side
and `node.dist()` for the rest. `node.net()` is used only by `Core` and
`machines.rs`; no route of section 8 and no mod reaches it (APP-F-61).

## 10. Test driver (feature `driver`)

Only for tests. It adds nothing to any webview: it uses the native
`eval_with_callback` from the Rust side (colos probe `app-driver-macos`:
20 of 20 runs, 3000 of 3000 callbacks).

```rust
#[cfg(all(feature = "driver", not(debug_assertions)))]
compile_error!("the driver feature is only for debug test builds");
```

A driver build reads `WATANE_DRIVER_SCREEN` once into `AppState` at startup:
`hidden` (also unset or unknown), `background`, or `front`. On macOS, setup
sets `ActivationPolicy::Accessory` for hidden/background (no Dock icon),
and startup disables activation ignoring other apps. One helper in `views`
applies the mode last to all three builders of section 5: hidden uses
`visible(false).focused(false)`, background uses `visible(true).focused(false)`,
and front leaves the builder unchanged. A second helper makes focus and
user-attention calls only in front, including reopening a mod. Without
`driver`, builders and focus/attention behavior remain as in section 5;
no screen environment variable or driver code is compiled into a release.

On Linux, driver builds allow automatic script popup attempts in WebKitGTK
so they reach the native new-window deny handler; the handler still denies
every request. Production WebKitGTK settings are unchanged (NOTES S18).

Transport: one JSON object per line; requests on stdin; responses and
events on stdout. All logging goes to stderr. Request
`{"id": <u64>, "op": "<op>", ...}`; response `{"id": n, "ok": <value>}` or
`{"id": n, "err": "<text>"}`. Responses can arrive out of order. After
setup and the first page load of the startup window (`main` or
`mod-<local>`), the app prints
`{"event": "ready", "port": <u16>}`, or `{"event": "failed", "cause": "..."}`.

| op | Fields | ok value |
|---|---|---|
| `eval` | `label`, `js` | the string that `eval_with_callback` returns (JSON text) |

dist with `Options::listed_local` true, so the journey tests (J5) can serve

## 11. Test plan

`cargo test` runs the unit and static tests. `cargo test --features driver`
also runs the quiet window tests; on macOS they need a logged-in session.
For Linux, run `app/scripts/linux-test.sh` from any directory (or
`./scripts/linux-test.sh` here). It builds `linux.Dockerfile` and runs both
the default suite, then the driver suite under `xvfb-run` with Openbox, including ignored
slow tests such as J2. It compiles but skips every front test by name.
Extra arguments (for example `ac5_journey_j2`) go to both cargo runs.
Named Docker volumes cache Cargo’s registry and `/linux-target`; the
worktree’s macOS `target/` is untouched. The runner prints the image’s GLib,
libsoup and WebKitGTK versions before testing.
Window tests spawn `env!("CARGO_BIN_EXE_watane-app")` with a temporary home
and `--port 0`, and talk to it through `tests/support/`.

The constructors have the same `(home: &Path, env: &[(&str, &str)]) -> App`
signature. `App::start` selects hidden; `App::background` selects background;
`App::front` selects front. Each overrides the caller's screen environment.
Tests declare their mode through these constructors, with no mode branch
in their bodies. The default suite uses start/background. The background
mode probe is the sole quiet test asserting `visible == true`.

Every test of real focus (`focused == true`, `document.hasFocus()`), visible
front windows, stacking, or the 800 ms approval gate uses `App::front` and
`#[ignore = "front: takes the screen"]`. Front waits for at least 30 s of
human idle time from `ioreg -c IOHIDSystem`'s `HIDIdleTime` nanoseconds,
prints `waiting for you to step away` once to stderr, and panics after
10 minutes instead of skipping. Idle parsing is pure and unit-tested in
`support_selftest`. The foreman runs front tests explicitly; ordinary
`cargo test --features driver` never runs them. Front checks
`ioreg -n Root -d1` before spawning and on every idle poll, and on a locked
screen passes early with the stderr line
`front test skipped: the screen is locked (CGSSessionScreenIsLocked)`,
visible even without `--nocapture`.

The hidden shell probe checks page loads, native eval, an 800 ms timer's
latency, visibility, focus and the actual Accessory policy. Isolation tests
exercise the hostile page's timer-driven poll loop hidden. Record the
observations and any tests requiring background due to hidden WKWebView
scheduling in `NOTES.md`. The consent page intentionally keeps approval
disabled without document focus: the hidden field/withhold test enables
the button through native eval; only the ignored front test proves the
real approval gate. No production security check changes.

```rust
    #[error(transparent)] Tauri(#[from] tauri::Error),
}
#[derive(Debug, Serialize)]
pub struct CmdError { pub code: &'static str, pub message: String }
```

`CmdError.code` is one of `refused`, `not_found`, `bad_input`,
`missing_providers`, `unavailable`, `host`, `dist`, `io`, and from stage G
`net` (a `NetError` or `NodeError`, 9.8). The host's own
code replaces `host` when it has one (HOST-F-20). `message` is the whole
cause chain: start with `{e}` and append each `source()` with `: ` unless
that cause is already present as a whole `: `-delimited part of the text
(including its beginning or end),
so no cause is hidden or printed twice (F-QUAL-3). dist already escapes untrusted
text in its `Display`. Display is used for package errors and URLs; no Debug
or serde diagnostic reaches the error line. Each main-window action has an
increasing id; starting it clears the line. Its asynchronous errors (including
refreshes) may update the line only while that id is still the latest.

Wrong-channel follows use `words::wrong_channel`:
`<url> serves <found label>, not <expected label>`. Labels use locally stored
profiles through `words::party`/`party_label`, `you` for the own identity,
and the fingerprint otherwise. Mod refresh failures use `words::channel_read`
and `index_read` to name the channel before its cause. The fetch route's
malformed-body response retains the JSON rejection body text (section 8.3).

Busy-port startup uses `words::port_in_use(P)`:
`Port P is in use, maybe by another watane app. Start this one with --port <n> or WATANE_PORT=<n> to use another port, or --port 0 for any free port.`
The app stays open to show this; it never chooses another port by itself.

### 17.3 HostConfirm::manage

`HostConfirm` (9.2) implements `Confirm::manage` and `Confirm::reduced`.
`manage` runs each `Ask` as the app's own button does, with the manager
named, and maps the result: the change made gives `Approved`; a `Deny`
of the participant, or the host's `refused` after one, gives `Denied`;
any other error gives `Failed(<its text>)`.

Host polls this future on its own small runtime. `manage` posts its async
work to the app runtime and awaits the join handle; dist work remains in
the existing blocking tasks on that runtime. Dropping the host future
aborts the app task, so a pending manage consent cannot later act. No
second app runtime is created.

| `Ask` | The app |
|---|---|
| `Install { release, link }` | If `link` is set and names a channel that dist does not already read (own, followed, or a chosen index), first `Request::Read` (17.4), with no network request before the answer (host Q30, answered b). A deny ends the request `Denied` and reads nothing. On approve, the app reads the link with `node.read_link`, retaining its verified `Fetched` and link for planning and `follow_fetched`. Unlike `open_link`, this does not follow before the install. The existing dist checks for listed locations still apply. Then, for every request, the path of `install_release` (7), with a pick request (9.7) when a provider is missing, and `host.install(plan, Requester::Mod(by))`, whose consent shows as for any manager install. After an install from a link that was read this way, the channel is followed as `install_link` follows it (`follow_fetched`); a read that leads to no install follows nothing. Without a link, or with a link of a channel already read, dist fetches only through the bases it already holds (dist 5.11). |
| `Update(local)` | The offer of that mod (`ModView.offer`, 9.5); none gives `Failed("no update is offered for <name>")`. Else install it as `Install` does, with `Requester::Mod(by)`. |
| `Enable(local)` | `Request::Manage` with `Enable`; on approve, `host.enable`. |
| `Grant { local, grant }` | `Request::Manage` with `Grant` and the grant line; on approve, `host.grant`. |
| `Remove { local, delete_data }` | `Request::Manage` with `Remove` or `RemoveData` and the users of APP-F-67; on approve, what `mod_remove` does: `views::close_mod`, `host.remove(local, delete_data)`, and the main mod file of 5.4. |

`HostConfirm::install` with `Requester::Mod(by)` builds `Request::Install`
with `asked_by` set (17.4); the host asks it for every such plan (host
12.1), so an update with no new grant shows too (APP-F-72).

`reduced(by, reduction)` must not block: it posts to the main thread and
returns. `OpenPage(local)` (host Q31) opens or focuses `mod-<local>` as the
Library's Open does (`views::open_mod`), unless a consent request is open

### 17.4 Consent requests

```rust
// Request::Install and Request::Pick gain, with #[serde(default)]:
//     asked_by: Option<Asker>,                      // step 10: the manager that asked
// Absent askers are omitted when serialized to preserve earlier request JSON.
pub enum Request {
    // ... the variants of 6.2, and:
    /// Step 10 (17.3): an enable, a grant or a removal that a manager asks for.
    Manage { asked_by: Asker, action: ManageAction, target: Target,
             grant: Option<GrantLine>, users: Vec<String> },
    /// S82 (host Q30): a manager names a link of a channel this home does not read.
    Read { asked_by: Asker, link: String, release: String },
}
#[derive(Clone, Debug, PartialEq, Serialize, Deserialize)]
pub struct Asker { pub local: String, pub name: String, pub publisher: Option<Party> }   // None = local
#[derive(Clone, Debug, PartialEq, Serialize, Deserialize)]
pub struct Target { pub local: String, pub name: String, pub version: String, pub publisher: Option<Party> }
#[derive(Clone, Copy, Debug, PartialEq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum ManageAction { Enable, Grant, Remove, RemoveData }
```

A `Manage` request takes only `Approve` with no `withheld`, or `Deny`
(`WrongAnswer`), as `Join` does (6.1). `grant` is set only for `Grant`;
`users` holds the APP-F-67 names (the enabled mods that call it or
receive its events) only for `Remove` and `RemoveData`.

The consent page (6.3): every request with `asked_by`, including `manage`,
starts with `Asked by <asker>, which manages your mods`. This names the
asker's publisher or local status (APP-F-71); the table lists the remaining
lines for `manage`.

| Request | Title | Lines |
|---|---|---|
| `install` with `asked_by` | as 6.3 | first line `Asked by <asker>, which manages your mods`; the rest as 6.3 |
| `pick` with `asked_by` | as 6.3 | the same first line |
| `manage`, `enable` | `<asker name> asks to turn on <target name>` | the target as an install block names it (name, version, party or `local`) |
| `manage`, `grant` | `<asker name> asks to give <target name> a grant` | the target; the grant line, with no checkbox |
| `manage`, `remove` | `<asker name> asks to remove <target name>` | the target; `Its data is kept. Installing it again brings it back.`; `Used by: <users>` when not empty |
| `manage`, `remove_data` | `<asker name> asks to remove <target name> and delete its data` | the target; `Its data is deleted. This cannot be undone.`; `Used by: <users>` when not empty |
| `read` (S82) | `<asker name> asks to read <link>` | the first line; `To install <release>, this home reads the channel of this link. It has not read it before.` |

A `Read` request takes only `Approve` with no `withheld`, or `Deny`, as
`Manage` does.

**Stop asks** (S82, host Q32, answered b). Every request with `asked_by`
(`install`, `pick`, `manage`, `read`) shows a third button, `Deny and stop
asks from <asker name>`, after `Deny`. It is not gated by the 800 ms rule
(it only reduces) and never has the focus at load. A click sends
`consent_answer({id, approve: false, withheld: [], choice: null, stop: true})`:
the app answers `Deny`, then withdraws the asker's `manage` grant with
`host.revoke(<asker local>, Grant::Manage)`, as the details switch does. So
the request reads `denied`, and the manager's next request traps
`not_granted` until the participant gives the grant back. `stop: true` on a
request without `asked_by` is `WrongAnswer`. `stop` is optional and false
by default, so earlier callers are unchanged.

The buttons, the focus rule, the 800 ms gate and the mark are those of
6.3 and 6.4: a manager cannot cover, imitate or answer the consent view
(APP-F-71). Every untrusted string, the asker's name included, is set
with `textContent`.
